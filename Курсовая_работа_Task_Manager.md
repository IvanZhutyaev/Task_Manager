# ВВЕДЕНИЕ

Сейчас почти любая команда — разработка, маркетинг, учёба, небольшой бизнес — ведёт задачи не в блокноте, а в электронном трекере. Нужно понимать, кто что делает, какой статус у работы, какой срок и кто отвечает. Без этого быстро появляются «потерянные» задачи и хаос в чатах. Сообщения в мессенджере живут короткое время: важные договорённости уезжают вверх ленты, а через неделю уже никто не помнит, кто взял на себя конкретный пункт.

Я сталкивался с этим и на учёбе, и в учебных командных проектах: пока задачи живут только в мессенджере, всегда найдётся человек, который «думал, что это делает кто-то другой». Трекер не решает все проблемы коммуникации, но хотя бы делает работу видимой. Когда у задачи есть владелец, статус и срок, споры «кто виноват» сменяются вопросом «что сделать дальше». Для курсовой это особенно важно: тема должна быть понятной без долгого объяснения предметной области, и при этом достаточно богатой, чтобы на ней можно было показать backend, клиентов и инфраструктуру.

В курсовой работе я разрабатываю систему **Task Manager** — учебный, но рабочий сервис управления задачами. Главная идея проекта: **один backend (REST API)** и **несколько клиентов** к нему:

- веб-приложение (SPA в браузере);
- мобильное приложение на Android;
- консольный клиент (CLI) на Python.

Такой подход близок к реальной разработке продуктов: сервер хранит бизнес-логику и данные, а интерфейсы можно менять и добавлять отдельно. Если завтра понадобится ещё один клиент — например, интеграция с ботом или скриптом отчётности, — достаточно соблюдать тот же контракт `/api/v1`, а не дублировать правила доступа в каждом интерфейсе.

Тема работы может быть сформулирована и как **универсальный REST API для многопользовательского управления задачами**: универсальность здесь означает не «поддержка любых предметных областей», а то, что один и тот же API обслуживает разные типы клиентов и разные роли пользователей. Web закрывает повседневную работу с доской, Android — доступ вне рабочего места, CLI — проверку и автоматизацию без GUI.

**Цель работы** — спроектировать и реализовать систему управления задачами с единым API и клиентами Web, Android и CLI, а также показать её работоспособность на сквозных сценариях.

**Задачи:**

1. разобрать предметную область и аналоги;
2. обосновать стек технологий;
3. спроектировать архитектуру и модель данных;
4. реализовать backend на Java / Spring Boot;
5. реализовать клиенты Web SPA, Android и CLI;
6. собрать окружение в Docker Compose;
7. проверить систему тестами и ручными сценариями.

**Объект** — программные системы управления задачами.  
**Предмет** — проектирование и реализация многоклиентского сервиса на базе REST API.

Практическая значимость работы для меня как студента в том, что получился законченный прототип, который можно запускать локально и развивать дальше. Его можно показать как портфолио: есть репозиторий, воспроизводимый стенд, документация API через OpenAPI и понятный пользовательский сценарий от регистрации до перемещения задачи по доске. Дальнейшее развитие естественно ложится на облачный деплой, усиление Android-клиента и расширение отчётности, но уже сейчас система закрывает основной цикл управления задачами.

Методически я шёл от контракта к интерфейсам. Сначала были сущности, роли и endpoint’ы, затем — клиенты, которые эти endpoint’ы вызывают. Такой порядок помог избежать ситуации, когда веб-страница «живёт своей жизнью», а мобильный клиент потом не может повторить те же действия. Docker Compose появился не в самом конце «для красоты», а как способ зафиксировать окружение: PostgreSQL, API и SPA поднимаются вместе, и меньше шансов получить расхождение «у меня локально другая база».

Структура работы: введение; глава 1 (теория); глава 2 (практика); лист с итоговой работой; бизнес-кейс; заключение; список источников; приложение. В теоретической части я разбираю предметную область, аналоги, рынок и стек. В практической — требования, архитектуру, модель данных, реализацию API и клиентов, развёртывание и проверку. Зарплаты и рыночная аналитика опираются на открытые обзоры 2025–2026 годов с фиксацией даты обращения; это ориентиры, а не претензия на полный статистический отчёт.

Отдельный акцент работы — именно на серверном контракте. Я мог бы сделать «красивую доску» только в браузере и остановиться. Но тогда не было бы доказательства, что система годится для разных клиентов. Поэтому в тексте и в реализации постоянно повторяется связка: пользователь → JWT → проверка прав → изменение данных → одинаковый результат во всех интерфейсах. Эта связка и есть практический смысл формулировки про универсальный REST API.

# Глава 1. Теоретическая часть

## 1.1. Введение в тему

Системы управления задачами (task trackers / project management tools) — это программы, где команда фиксирует работу в виде задач, статусов, сроков и ролей. В простых продуктах достаточно доски Kanban: колонки «Сделать», «В работе», «Готово» и карточки-задачи. В более сложных появляются организации, команды, права доступа, спринты, метки, комментарии, уведомления и отчёты. Между этими полюсами лежит большая зона «лёгких командных трекеров», куда по замыслу и попадает мой учебный Task Manager.

Такие системы нужны не только разработчикам. Маркетинг ведёт кампании и дедлайны, учебные группы распределяют части курсовой, небольшой бизнес фиксирует заказы и ответственность исполнителей. Общая идея одна: работа должна быть видимой, а статус — общим для всех участников. Если статус хранится только в голове одного человека, команда зависит от его доступности. Если статус в системе — любой участник с правом чтения может понять текущую картину.

В Task Manager ставка сделана на **данные, доступ и согласованность между клиентами**:

- **мобильный клиент** — задачи смотрят не только за компьютером;
- **веб-клиент** — основной «рабочий стол»;
- **API и CLI** — для инженеров и интеграций.

Современный подход часто называют **API-first**: сначала продумывается серверный контракт, потом вокруг него собираются интерфейсы. Именно так устроен мой проект. Это упрощает развитие: новый клиент не требует переписывать бизнес-логику, если REST-контракт уже стабилен. На практике API-first также дисциплинирует модель данных: нельзя «спрятать» важное правило только в HTML-форме, потому что Android и CLI всё равно пойдут через те же endpoint’ы.

Базовые сущности почти у всех трекеров похожи: пользователь и роли, проект, доска и колонки, задача (приоритет, срок, исполнитель, статус), а также организации, команды, метки, спринты и приглашения. Разница между продуктами обычно не в том, что «задача есть или нет», а в глубине процессов: насколько гибкий workflow, насколько богатый поиск, какие отчёты и интеграции доступны «из коробки».

Kanban делает поток работ видимым: ограничение незавершённой работы (WIP), быстрое обнаружение «заторов», понятный статус. Карточка движется по колонкам, и это движение само по себе сообщает о прогрессе. Scrum добавляет итерации (спринты), планирование и ретроспективы. В курсовой я опирался в первую очередь на канбан-модель (колонки и карточки), потому что она нагляднее для демонстрации и хорошо ложится на UI. При этом в модели данных и API предусмотрены сущности вроде спринтов и меток, чтобы прототип не выглядел тупиковым.

Даже в небольшом сервисе нельзя делать «все видят всё»: нужны роли проекта, режимы досок, приглашения. Иначе любой зарегистрированный пользователь потенциально получает доступ к чужой работе. Также важны комментарии, чеклисты, уведомления и поиск — признаки настоящего трекера. В API у меня часть этих вещей реализована сразу, а в клиентах раскрыта в разной степени. Это осознанный компромисс учебного проекта: сначала крепкое ядро, потом равномерное покрытие UI.

Отдельно стоит сказать про многопользовательский режим. «Многопользовательский» — не просто «несколько аккаунтов в таблице users». Это совместная работа в рамках организации и проекта, разграничение прав OWNER / EDITOR / VIEWER / CONTRACTOR, приглашения и режимы доступа к доскам. Без этого Task Manager был бы личным блокнотом с красивым API, а не системой управления задачами команды.

Ещё один слой темы — жизненный цикл задачи. В минимальном виде он выглядит так: задача появляется в колонке «Сделать», берётся в работу, при необходимости уточняется комментариями и чеклистом, затем уходит в «Готово». В более развитом виде появляются метки, приоритеты, сроки, исполнитель и связь со спринтом. Даже если UI показывает не все поля сразу, модель должна допускать эти атрибуты, иначе расширение продукта превращается в ломку схемы. В курсовом Task Manager я старался заложить именно такую «расширяемую середину»: канбан понятен с первого взгляда, а сервер уже знает про роли, организации и дополнительные сущности совместной работы.

## 1.2. Актуальность проекта

**1. Распределённая работа.** Удалёнка и гибридный формат стали обычными. Команде нужен общий список задач, а не переписка «напомни, пожалуйста». Когда люди находятся в разных городах и часовых поясах, асинхронность становится нормой: нельзя рассчитывать, что все одновременно смотрят один чат. Трекер как раз и даёт асинхронную общую картину.

**2. Несколько устройств.** Один и тот же человек может начать задачу в браузере и проверить статус с телефона. Значит, логично делать общий backend. Если данные живут только в локальном приложении или только в одной веб-форме без нормального API, второй клиент неизбежно превращается в костыль. В моём проекте Web, Android и CLI читают и пишут одни и те же сущности.

**3. Права и совместная работа.** Важно не только создать задачу, но и ограничить доступ: кто владелец проекта, кто редактор, кто только смотрит, кому открыта конкретная доска. Для учебных и небольших продуктовых команд это критично: внутри одной организации могут быть разные проекты с разным составом участников. Режимы OPEN / PRIVATE / TEAM_ACL показывают, что доступ — часть предметной области, а не «галочка в админке».

**4. Ситуация на рынке ПО в России.** После ограничений и ухода части зарубежных вендоров вырос интерес к отечественным и самостоятельно разворачиваемым трекерам. По открытым обзорам (Naumen и отраслевые материалы 2024–2026) доля российских таск-трекеров заметно выросла; крупный бизнес часто сохраняет гибридные схемы. Тема «своя система управления задачами» не абстрактная, а рыночная. Даже если конкретная компания покупает SaaS, навыки проектирования API, ролей и self-hosted контура остаются полезными.

**5. Учебная ценность.** На одном проекте закрываются backend, БД, безопасность, веб, Android, CLI и Docker. Такой набор ближе к реальной работе над продуктом, чем отдельная лабораторная по одному языку. Я вижу в этом практический смысл: проще объяснить работодателю или преподавателю, что умеешь, когда есть связный сервис, а не пять несвязанных упражнений.

Я сознательно сделал три клиента, потому что это показывает зрелость API: если контракт нормальный, к нему можно подключить и браузер, и Android, и скрипт. Если же API заточен только под один HTML-шаблон, второй клиент сразу начинает «ломаться» на деталях ответа и правах доступа. Кроме того, CLI помогает быстро проверять стенд после `docker compose up`: health, login, создание проекта и задачи можно прогнать без открытия браузера.

Актуальность усиливается и тем, что Task Manager демонстрирует универсальный REST API как центр системы. Универсальность здесь — инженерная: один контракт для разных клиентов и сценариев. Именно такой навык часто ждут от junior/middle backend-разработчика: уметь спроектировать ресурсную модель, авторизацию и стабильные ответы, а не только «нарисовать страницу».

Есть и организационная сторона актуальности. В маленькой команде отсутствие трекера редко заметно в первую неделю. Проблемы накапливаются позже: теряются договорённости, сложно вводить новичка, невозможно понять загрузку людей. Когда команда вырастает хотя бы до пяти–семи активных участников, «память чата» перестаёт масштабироваться. Поэтому учебный проект на тему Task Manager хорошо стыкуется с реальной практикой студенческих и небольших рабочих групп: боль знакома, а решение можно собрать своими руками и понять изнутри.

## 1.3. Актуальность выбранного технологического стека

| Часть | Технологии |
|-------|------------|
| Backend | Java 17, Spring Boot 3.2, Spring Security, Spring Data JPA, Validation |
| Auth | JWT (jjwt) |
| БД | PostgreSQL 16, миграции Liquibase; H2 в тестах |
| Документация API | Springdoc OpenAPI (Swagger) |
| Web | HTML, CSS, JavaScript (SPA), Nginx |
| Android | Kotlin, Android SDK 34, OkHttp, Gson, Coroutines, Material |
| CLI | Python 3 (`argparse`, `urllib`) |
| Инфраструктура | Docker, Docker Compose |

**Java и Spring Boot.** Spring Boot — распространённый каркас для backend на Java в банках, ритейле, телекоме и продуктовых компаниях. Netflix в публичных материалах описывает стандартизацию тысяч Java-сервисов на Spring Boot. В российских вакансиях Spring Boot обычно входит в базовый набор Java-backend вместе с JPA, PostgreSQL, Docker и REST. Для курсовой это удобно ещё и тем, что экосистема зрелая: валидация, security, миграции и OpenAPI подключаются предсказуемо.

**PostgreSQL.** Зрелая открытая СУБД, хорошо моделирует связи проект → доска → колонка → задача. В Docker-стенде сразу видны миграции, ограничения и реальные ошибки драйвера. Выбор PostgreSQL вместо «только H2» был принципиален: часть дефектов (например, с типизацией параметров поиска) проявляется именно на боевой СУБД.

**JWT + REST.** Для SPA и мобильных приложений часто делают stateless-аутентификацию: клиент получает токен и передаёт его в заголовке. Это упрощает горизонтальное масштабирование API и одинаково работает для браузера, Android и CLI.

**Kotlin / Android.** С 2019 года Google рекомендует Kotlin как предпочтительный язык для Android. Coroutines упрощают асинхронные сетевые вызовы, Material даёт привычный мобильный UX.

**Python CLI.** Быстро пишется и читается; стандартной библиотеки достаточно для HTTP. Для учебного проекта это плюс: не нужно тащить тяжёлый SDK, чтобы показать, что API самодостаточно.

**Docker Compose.** Удобен для локального стенда API + БД + фронт. Одна команда поднимает связанный набор сервисов, и меньше шансов услышать «у меня локально всё по-другому».

Почему не другой стек:

- Node.js/Express тоже подходит для API, но Java/Spring ближе к enterprise-вакансиям;
- React/Vue усилили бы SPA, но добавили бы сборку и время; vanilla JS закрыл нужный UX;
- Retrofit на Android был бы удобнее OkHttp, но OkHttp проще и достаточен;
- MongoDB хуже подходит для жёстких связей project/board/column/task.

В итоге стек выбран не ради хайпа, а потому что он совпадает с требованиями вакансий и удобен для сопровождения учебного прототипа. Он также хорошо иллюстрирует слои: язык и фреймворк backend, СУБД и миграции, клиенты разных платформ, контейнеризация.

## 1.4. Популярные аналоги проекта

### Jira (Atlassian)
Мощный корпоративный трекер для IT и Agile: спринты, workflow, интеграции, богатый REST API. Плюсы — гибкость и экосистема; минусы для небольших команд — сложность и стоимость владения. Jira часто выбирают там, где нужны сложные статусы, согласования и отчётность для больших команд разработки. Мой проект — учебный прототип с похожими сущностями (проекты, доски, задачи, роли), без глубины процессов Atlassian. Я не пытался повторить схему issue types, custom fields и permission schemes — это отдельный пласт продукта.

### Trello (Atlassian)
Простые визуальные Kanban-доски, быстрый старт. Trello силён тем, что пользователь за минуты понимает модель «колонка + карточка». Мой Web SPA ближе к Trello по идее колонок и карточек, но дополнительно есть организации, команды и режимы доступа к доскам. То есть визуально прототип «лёгкий», а по модели доступа ближе к более серьёзным командным системам.

### Asana
Управление работой команд: списки, доски, сроки, цели. Сильнее в проектном управлении для бизнеса и межотдельской координации; мой проект сильнее заточен под API и несколько клиентов. Asana хорошо показывает, что трекер — не только IT-инструмент, но для курсовой мне важнее инженерная сторона: контракт, роли, multi-client.

### YouTrack (JetBrains)
Трекер для команд разработки, гибкие поля и поиск. Готовый коммерческий продукт; у меня — самостоятельная реализация ядра. YouTrack интересен как пример сильного поискового и issue-oriented подхода, но повторять его query-язык в учебном объёме нецелесообразно.

### Яндекс Трекер и другие российские решения
Яндекс Трекер, Kaiten, WEEEK и др. закрывают нишу после ограничений на зарубежные сервисы. Это полноценный SaaS; мой Task Manager — свой код и контейнерный запуск. Сравнение с ними полезно именно в контексте РФ: рынок живой, спрос на управление задачами не исчез вместе с усложнением доступа к части зарубежных инструментов.

| Критерий | Jira | Trello | Яндекс Трекер | Task Manager |
|----------|------|--------|---------------|--------------|
| Kanban-доски | да | да | да | да |
| Роли и доступы | очень гибко | базово | гибко | да |
| Организации/команды | да | ограничено | да | да |
| Web / мобильный | да / да | да / да | да / да | SPA / Android |
| CLI/API | богатый API | API | API | CLI + REST |
| Self-host / свой код | сложно | облако | облако | репозиторий + Docker |
| Масштаб | enterprise | малые/средние команды | РФ / mid-market | учебный прототип |

Если коротко сравнить роли продуктов: Jira — тяжёлые процессы разработки; Trello — быстрый визуальный канбан; Asana — координация разных отделов; YouTrack — удобен в экосистеме JetBrains; Яндекс Трекер и Kaiten — варианты, которые чаще рассматривают в РФ. Мой Task Manager ближе к пересечению Trello по UI-идее и «лёгкой Jira» по ролям и доступам, но в учебном масштабе.

Из аналогов я сознательно не копировал сложные workflow, enterprise-аналитику и marketplace плагинов. Фокус — auth, оргструктура, канбан, права, multi-client, Docker. Такое сужение темы позволило довести прототип до рабочего состояния, а не остановиться на половине «как у большого продукта» функций.

Важный вывод из сравнения: коммерческие системы конкурируют сервисом, экосистемой и поддержкой. Учебный проект конкурировать с ними «в лоб» не должен. Его ценность — в прозрачности реализации универсального REST API и в том, что студент может объяснить каждую сущность, каждое право доступа и каждый клиентский сценарий.

Сравнение также помогает выбрать, что не делать. Я не стал уводить проект в сторону сложных issue-связей, иерархии эпиков или конструктора произвольных workflow. Эти функции полезны, но для курсового объёма они размывают фокус. Вместо этого я усиливал то, что отличает именно мой прототип: self-hosted запуск, явные роли, несколько клиентов и проверяемый контракт. Если смотреть на таблицу сравнения, Task Manager проигрывает коммерческим системам по зрелости процессов, но выигрывает как учебная площадка, где весь код и весь путь запроса можно проследить от кнопки до строки в PostgreSQL.

### Зарубежье

В США компенсации backend/Android часто считаются в год и для middle/senior обычно выше российских в валюте; в Европе вилки ниже американских, но тоже заметно выше средних российских. Даже если студент ориентируется только на российский рынок, совпадение стека с зарубежными практиками не мешает: те же идеи REST, JWT, контейнеров и мобильного клиента встречаются повсеместно.

Чаще платят больше при наличии Docker/CI, миграций PostgreSQL, Spring Security/JWT, multi-client API и современного Kotlin на Android. Эти пункты я старался закрыть в прототипе. Курсовая, конечно, не заменяет коммерческий опыт, но показывает, что выбранные технологии не случайны.

### Санкции и импортозамещение

После 2022 года часть зарубежных вендоров усложнила работу в РФ (часто приводят пример Atlassian/Jira), вырос спрос на российские трекеры и self-hosted контур. К 2025–2026 импульс «экстренного» импортозамещения ослаб: компании считают бюджеты жёстче. Исследования (в том числе Naumen) показывают, что полный уход с иностранного ПО происходит не везде — часто остаётся гибрид. Навыки Spring, PostgreSQL, Docker и Android при этом остаются востребованными: независимо от бренда трекера кому-то всё равно нужно писать интеграции, внутренние сервисы и клиентские приложения.

Для моей темы это означает две вещи. Во-первых, рынок управления задачами в РФ живой, и понимание предметной области полезно. Во-вторых, умение собрать свой контур с API и клиентами — практический навык, даже если итогом карьеры будет работа не над «ещё одним Trello», а над корпоративным сервисом со схожей архитектурой.

С точки зрения зарплатного фонда полезно разделять «знание синтаксиса языка» и «умение собрать сервис». Вилки middle-уровня чаще открываются тем, кто уже делал не учебный Hello World, а связку API + БД + auth + хотя бы один клиент. Курсовой Task Manager как раз даёт такую связку. Я не утверждаю, что одного прототипа достаточно для middle-оффера, но он ближе к ожиданиям рынка, чем изолированная лабораторная по коллекциям или одной Activity в Android.

## 1.7. Теория по стеку технологий

**REST.** Стиль построения веб-API: ресурсы имеют URI, действия выражаются HTTP-методами. В проекте основные операции идут через `/api/v1/...`. REST удобен тем, что любой запрос можно повторить через curl, CLI или Swagger. Ресурсная модель хорошо ложится на сущности трекера: организации, проекты, доски, колонки, задачи. Версия `v1` в пути фиксирует контракт и оставляет пространство для будущих несовместимых изменений без ломания старых клиентов сразу.

**Spring Boot.** Упрощает запуск приложения: меньше ручной конфигурации, встроенный Tomcat, стартеры Web/Security/JPA. Версия 3.x работает на Java 17+ и Jakarta-пакетах. Практически это значит, что я тратил время на предметную логику и права доступа, а не на ручную сборку сервлет-контейнера. Профиль `prod` позволяет подключать PostgreSQL в Docker, а тесты — использовать H2.

**Spring Security и JWT.** После входа клиент сохраняет токен и отправляет его в `Authorization: Bearer ...`. Сервер проверяет подпись и определяет пользователя. JWT удобен тем, что SPA и Android не требуют «липкой» серверной сессии на каждый клик. Для объёма курсовой достаточно рабочей схемы login/register без усложнения до полноценного OAuth2 Authorization Server. Важно понимать ограничение: JWT не заменяет проверку прав на каждый ресурс; токен говорит «кто пользователь», а сервис уже решает, можно ли ему читать конкретную доску.

**JPA и PostgreSQL.** JPA/Hibernate связывает классы с таблицами; Liquibase ведёт миграции схемы. H2 используется в тестах, основной стенд — PostgreSQL. Миграции нужны, чтобы схема воспроизводилась одинаково на любой машине. Без них легко получить ситуацию, когда «таблица есть у автора проекта, но нет у проверяющего».

**Web SPA.** Страница загружается один раз, дальше UI обновляется через JavaScript и запросы к API. Реализация на HTML/CSS/JS без тяжёлого фреймворка; статику отдаёт Nginx. Такой выбор уменьшил порог сборки и подчеркнул, что сервер — источник правды, а не серверный рендеринг форм.

**Android.** Activities, ViewBinding, OkHttp. На эмуляторе хост-машина доступна как `10.0.2.2`, API — `http://10.0.2.2:8080/api/v1`. Это важная практическая деталь: без понимания сетевого адреса эмулятора мобильный клиент «не видит» локальный backend.

**CLI на Python.** Те же HTTP-запросы без GUI: показывает самодостаточность API. CLI также удобен как тонкий слой автоматизации и smoke-проверки.

**Docker Compose.** Описывает и поднимает Postgres, API, SPA и CLI одним конфигом. Контейнеризация фиксирует версии и зависимости окружения.

Цепочка в проекте: логин → JWT → REST API → проверка прав → JPA/PostgreSQL; тот же сценарий повторяется из CLI. Теоретически это классическая схема современного многоклиентского сервиса. Практически она заставляет держать в голове границы ответственности: клиент рисует UI и отправляет запросы, сервер валидирует и применяет правила, база хранит согласованное состояние.

Отдельно отмечу OpenAPI/Swagger: интерактивная документация помогает и при разработке клиентов, и при проверке контракта. Когда endpoint’ов становится много, возможность увидеть схемы запросов и ответов снижает число ошибок «не тот путь» и «не то поле».

Если собрать теорию в одну схему, получается цепочка ответственности. Клиент отвечает за удобство и корректный вызов API. Spring Security отвечает за аутентификацию запроса. Сервисный слой отвечает за авторизацию и бизнес-правила. JPA/репозитории отвечают за сохранение состояния. PostgreSQL отвечает за целостность данных на уровне ограничений. Docker Compose отвечает за то, чтобы эта цепочка одинаково поднималась у разных людей. Понимание этих ролей важнее заучивания отдельных аннотаций: именно оно позволяет потом менять UI или добавлять клиент, не ломая систему целиком.

# Глава 2. Практическая часть

## 2.1. Постановка задачи и требования

Нужно было сделать систему, в которой пользователь может:

1. зарегистрироваться и войти;
2. создавать организации, команды и проекты;
3. работать с досками, колонками и задачами;
4. управлять ролями и доступом;
5. работать с приглашениями;
6. пользоваться клиентами Web SPA, Android и CLI;
7. поднимать стенд через Docker Compose.

Нефункциональные требования: понятный REST-контракт, проверка прав, воспроизводимый локальный запуск, корректные ответы на некорректный ввод.

Этапы разработки:

1. backend-ядро (API, сущности, auth);
2. базовый Web-клиент и проверка сценариев;
3. Android-клиент;
4. CLI и Docker;
5. исправление дефектов (ошибка списка задач в Postgres, незакрывающиеся dialog в SPA и др.).

Такой порядок логичен: сначала контракт и данные, потом интерфейсы, потом упаковка стенда.

### Функциональные требования

- FR1. Регистрация и аутентификация пользователя.  
- FR2. CRUD организаций и управление участниками.  
- FR3. Создание команд и добавление людей в команды.  
- FR4. Создание проектов и назначение ролей.  
- FR5. Создание досок с режимом доступа.  
- FR6. Создание колонок и задач.  
- FR7. Редактирование атрибутов задачи и перемещение между колонками.  
- FR8. Приглашения в проект.  
- FR9. Работа минимум через Web, Android и CLI.

### Нефункциональные требования

- NFR1. API должно быть пригодно для разных клиентов.  
- NFR2. Ошибки клиента не должны выглядеть как «падение сервера», если входные данные некорректны.  
- NFR3. Локальный запуск должен воспроизводиться через Docker.  
- NFR4. Базовые сценарии должны проходить без ручной правки БД.

Критерий готовности для меня звучал так: после чистого `docker compose up` можно зарегистрировать пользователя, создать проект с доской, добавить задачу, переместить её и увидеть тот же результат из другого клиента. Если этот цикл не проходит, система ещё не готова, даже если отдельные экраны «почти работают».

## 2.2. Архитектура системы

```text
Web SPA  (:3000)  ---|
Android              |--->  Spring Boot API (:8080)  --->  PostgreSQL (:5432)
CLI (Python)      ---|
```

Принципы:

- вся бизнес-логика на сервере;
- клиенты не ходят в БД напрямую;
- один и тот же токен/пользователь работает во всех клиентах;
- Compose поднимает связанный набор сервисов.

На том же API есть демо-UI на Thymeleaf (`:8080`), но основным веб-клиентом остаётся SPA на порту 3000. Thymeleaf удобен как быстрая серверная витрина, но для идеи универсального REST API важнее независимый SPA: он общается с backend ровно так же, как Android и CLI.

Слои backend:

- **controllers** — принимают HTTP, отдают DTO;
- **services** — бизнес-правила и права;
- **repositories** — доступ к данным;
- **security** — JWT-фильтр и контекст пользователя;
- **exception handler** — единый формат ошибок.

Такое разделение помогло держать код читаемым. Контроллер не должен решать, можно ли contractor’у видеть задачу: это зона сервиса. Репозиторий не должен знать про HTTP-статусы. Exception handler приводит ошибки валидации и доменные исключения к предсказуемому JSON, чтобы клиенты могли одинаково показывать сообщения пользователю.

С точки зрения развёртывания архитектура «три клиента + один API + одна БД» проста, и в этом её сила для учебного проекта. Нет микросервисного зоопарка, но уже есть чёткая граница: UI отдельно, домен отдельно, данные отдельно. Если позже выделять отдельные сервисы уведомлений или поиска, контракт `/api/v1` останется точкой интеграции.

Межклиентская согласованность достигается не «синхронизацией приложений друг с другом», а общим сервером. Web не пушит состояние в Android напрямую; оба читают актуальное состояние из API. Поэтому после `move` задачи в CLI достаточно обновить доску в SPA, чтобы увидеть новый столбец.

В архитектурном смысле я выбирал простоту сознательно. Можно было бы сразу рисовать очереди сообщений, отдельный сервис уведомлений и API gateway. Для курсовой это дало бы больше схем, но меньше законченного результата. Текущая монолитная схема backend при чётких слоях остаётся прозрачной: легче искать дефекты, проще поднимать стенд, понятнее объяснять поток запроса. Когда базовый контур стабилен, усложнять инфраструктуру уже имеет смысл; до этого момента лишние компоненты только маскируют проблемы модели и прав доступа.

## 2.3. Модель данных

Ключевые сущности:

- **User** — пользователь;
- **Organization** — организация;
- **Team** — команда внутри организации;
- **Project** — проект и роли участников (OWNER, EDITOR, VIEWER, CONTRACTOR и др.);
- **Board** — доска; режимы доступа OPEN / PRIVATE / TEAM_ACL;
- **BoardColumn** — колонка;
- **Task** — задача;
- метки, спринты, приглашения, уведомления, комментарии и чеклисты — для совместной работы.

Связи стандартные для трекера: проект содержит доски, доска — колонки, колонка — задачи. Пользователи связаны с оргструктурой и проектами через membership и роли. Такая иерархия позволяет масштабировать сценарии: от личного учебного проекта до небольшой организации с несколькими командами.

Инварианты: soft delete задач через `deletedAt`; contractor видит ограниченный набор задач; доступ к доске зависит от режима; пустой поисковый запрос не должен ломать выборку. Soft delete удобен тем, что случайно удалённые задачи не исчезают безвозвратно на уровне данных, а права contractor’а показывают, что модель доступа может быть тоньше, чем «участник проекта видит всё».

При проектировании я старался не смешивать «удобство UI» и «правду данных». Например, порядок колонок и атрибуты задачи хранятся на сервере; клиент лишь отображает и отправляет изменения. Это снижает риск расхождений между Web и Android.

На уровне модели важно также разделение организации и проекта. Организация задаёт широкий контур людей и команд, проект — конкретную область работы со своими ролями и досками. Такая двухуровневая структура привычна по коммерческим трекерам и позволяет не сваливать всех пользователей в одно плоское пространство. Для подрядной роли CONTRACTOR это особенно заметно: человек может быть нужен в проекте, но не должен автоматически видеть всё содержимое организации.

## 2.4. Серверная часть (API)

Backend: **Java 17 + Spring Boot 3.2**.

Реализовано: register/login и JWT; организации, команды, участники; проекты, доски, колонки, задачи; приглашения; поиск и уведомления на уровне API; метки и спринты; валидация; корректные 400 на некорректный JSON; Liquibase; профиль `prod` под PostgreSQL в Docker.

Важный исправленный дефект: при открытии колонки SPA запрашивает задачи без текстового поиска; PostgreSQL в связке с Hibernate получал `null` как `bytea`, и запрос падал с `function lower(bytea) does not exist`. Исправление: для пустого поиска передавать пустую строку и сравнивать `:q = ''`. Этот кейс хорошо показывает, почему учебный стенд должен включать именно PostgreSQL, а не только H2: часть проблем проявляется на конкретной СУБД.

Жизненный цикл запроса `GET /api/v1/columns/{id}/tasks`:

1. клиент вызывает endpoint с JWT;
2. фильтр достаёт пользователя из токена;
3. сервис проверяет право читать доску этой колонки;
4. репозиторий делает pageable-выборку с фильтрами;
5. ответ уходит в JSON (`content`, `page`, `size`, `totalElements`).

Аналогично устроены операции создания и перемещения задач: сначала идентификация, потом авторизация, потом изменение данных, потом DTO-ответ. Пагинация важна даже в учебном проекте: список задач не должен предполагать, что их всегда мало.

Документация через Springdoc OpenAPI помогает исследовать контракт без чтения всего кода контроллеров. Для CLI и Android это особенно полезно: видно пути, методы и тела запросов. Универсальность API проявляется в том, что один и тот же набор endpoint’ов закрывает сценарии разных клиентов без специальных «веб-only» костылей в бизнес-логике.

В серверной части я уделял внимание и качеству ошибок. Если клиент присылает некорректный JSON или нарушает валидацию полей, ответ должен быть 400-го класса, а не необработанным стектрейсом. Единый exception handler здесь экономит время всех клиентов сразу: Web, Android и CLI могут опираться на более предсказуемый формат. То же касается прав доступа: отказ должен быть явным. Иначе создаётся ложное ощущение, что «данные пропали», хотя на самом деле токену просто не хватает прав на доску или задачу.

## 2.5. Клиент Web SPA

Стек: HTML + CSS + JS, Nginx, порт **3000**.

Возможности:

- регистрация и вход;
- проекты и организации;
- канбан: создание и редактирование задач, перемещение, приоритет, срок, исполнитель;
- команды и приглашения;
- комментарии и чеклист в объёме UI.

Исправлен UX-баг: закрытый `<dialog>` оставался видимым из-за `display: flex` на всех dialog; flex оставлен только для `dialog[open]`. После этого «вечные» кнопки «Сохранить / Отмена» пропали. Баг выглядел мелко, но ломал ощущение готового продукта: пользователь не понимал, можно ли продолжать работу с доской.

SPA выбран вместо только Thymeleaf, чтобы веб-клиент ходил в те же endpoint’ы, что Android и CLI. Так проще показать идею API-first. Nginx отдаёт статику и позволяет держать веб-клиент как отдельный сервис в Compose. Для учебного проекта этого достаточно: не нужна сложная сборка фронтенда, но уже есть независимое клиентское приложение.

В повседневной демонстрации Web SPA — основной интерфейс. На нём удобнее всего показать полный путь: организация → проект → доска → задача → комментарий/чеклист. Android и CLI подтверждают, что те же данные доступны иначе, а не заменяют веб как главный UX.

С точки зрения реализации SPA держит состояние на клиенте только как кэш текущего экрана. Источник истины — API. Поэтому после действий в другом клиенте достаточно обновить данные доски, чтобы увидеть актуальные колонки и карточки. Такой подход проще, чем пытаться строить сложную realtime-синхронизацию на учебном этапе, и всё равно хорошо показывает согласованность системы.

## 2.6. Клиент Android

Стек: Kotlin, minSdk 26, target/compile SDK 34, OkHttp, Gson, Coroutines, Material.

Экраны:

- Auth — вход и регистрация;
- Home — проекты и организации;
- детали организации и проекта;
- Board — доска, создание колонок и задач.

API на эмуляторе: `http://10.0.2.2:8080/api/v1`. На реальном устройстве нужен IP компьютера в локальной сети. Эту настройку легко забыть, и тогда создаётся ложное впечатление, что «мобильный клиент не работает», хотя проблема в адресе хоста.

Android в текущей версии сильнее как клиент «создать и посмотреть»; часть сценариев удобнее в Web или CLI. Паритет клиентов не 1:1, но общий API один, и этого достаточно, чтобы показать кросс-платформенность. Я считаю такой компромисс честным для курсовой: важнее доказать работоспособность контракта, чем копировать каждый экран SPA на Kotlin.

Сетевой слой на OkHttp + Gson получился прозрачным: видно, какие заголовки уходят, как разбирается JSON, где обрабатываются ошибки. Coroutines позволяют не блокировать UI-поток во время запросов. Material-компоненты дают привычный вид форм и списков без глубокой кастомизации дизайна.

Для курсовой Android-клиент особенно полезен как «проверка на честность» API. Мобильное приложение не прощает размытых ответов и скрытых серверных допущений, которые иногда проходят в браузере за счёт ручных правок DOM или локальных костылей. Если register/login, список проектов и работа с доской проходят на эмуляторе через тот же `/api/v1`, значит контракт действительно клиентонезависимый, а не заточен только под SPA.

## 2.7. Клиент CLI

Стек: Python 3, файл `tm.py`.

Типовой сценарий:

```bash
python tm.py health
python tm.py register --email owner@demo.com --password secret12 --name Owner
python tm.py login --email owner@demo.com --password secret12
python tm.py projects --create "CLI Demo" --with-default-board --template KANBAN
python tm.py tasks <todoColumnId> --create "Сделать отчёт" --priority HIGH
python tm.py move <taskId> --column <doingColumnId>
```

После `move` в CLI обновление Web SPA показывает задачу в другой колонке — данные общие.

CLI нужен как демонстрация API без GUI, как smoke-тест после перезапуска Docker и как задел под автоматизацию. В отличие от браузера, CLI делает сценарий воспроизводимым текстом команд: его можно вставить в инструкцию запуска и повторить по шагам. Для инженера это привычный способ проверить, что backend «живой».

Ещё одно применение CLI — обучение контракту. Когда команда явно передаёт email, password, columnId и priority, становится видно, какие данные реально требует API. Это полезно и при отладке прав доступа: можно быстро проверить, что видит конкретный пользователь после login.

В репозитории CLI лежит рядом с остальными клиентами и использует тот же backend. Это важно методически: консольный клиент не «отдельная лабораторная», а часть одной системы. Если меняется путь endpoint’а или формат ответа, ломается не только SPA, но и `tm.py`. Такая связанность дисциплинирует изменения API и приближает учебный проект к реальной поддержке нескольких потребителей контракта.

## 2.8. Развёртывание в Docker

```bash
docker compose -p taskmanager up --build -d
```

| Сервис | Назначение | Порт |
|--------|------------|------|
| postgres | база | 5432 |
| api | Spring Boot | 8080 |
| web-spa | Nginx + SPA | 3000 |
| cli | контейнер CLI | — |

Проверка: `GET http://localhost:8080/api/v1/health` → `{"status":"UP"}`.

Типовые проблемы запуска: не запущен Docker Desktop; заняты порты 8080/3000; на Android забыли `10.0.2.2`; некорректный email при регистрации (валидация `@Email`). Большинство из них решаются проверкой окружения, а не правкой кода.

Compose важен как «сшивка» архитектуры. Без него легко получить рассинхрон: API запущен с одной конфигурацией, база — с другой, фронт смотрит не туда. С Compose зависимости выражены явно, а профиль `prod` у API рассчитан на работу с контейнерным PostgreSQL и миграциями Liquibase.

Для воспроизводимости я фиксирую проектное имя `-p taskmanager`, чтобы контейнеры и сети не смешивались с другими локальными экспериментами. После успешного старта логично проверить health, открыть SPA и только потом подключать Android или CLI.

Развёртывание в Docker также помогает отделить «ошибку кода» от «ошибки окружения». Если стенд поднимается одной командой, а сценарий всё равно падает, искать причину уже в логике API, правах или клиенте. Если же стенд не поднимается, сначала чинят Docker Desktop, порты и конфигурацию Compose. Для учебной сдачи и для совместной работы такой порядок экономит много времени.

## 2.9. Тестирование и демонстрация

Проверка:

1. Maven-тесты API;
2. smoke через HTTP/CLI (регистрация → проект → доска → задача);
3. ручной прогон SPA;
4. Android на эмуляторе при живом API.

Удобный порядок проверки:

1. Docker up, health OK;
2. Web: организация → проект → канбан;
3. Android: тот же пользователь и данные;
4. CLI: создание или перемещение задачи;
5. снова Web — данные совпали.

Сценарий успешен, если после регистрации можно войти во всех трёх клиентах; проект, созданный в одном клиенте, виден в другом; задача после `move` меняет колонку в SPA; некорректный JSON не даёт ложный 500; `docker compose up` поднимает healthy API.

Я отдельно проверял негативные случаи: неверный пароль, обращение без токена, попытка действий без прав, пустой или некорректный JSON. Для REST-сервиса это не менее важно, чем «счастливый путь». Если API на ошибках отвечает непонятно, клиенты начинают гадать, а отладка растягивается.

Демонстрационный сценарий лучше вести как одну историю одного пользователя. Например: зарегистрироваться как владелец, создать организацию и проект с канбан-шаблоном, добавить задачу с приоритетом, переместить её в колонку «В работе», зайти с Android под тем же аккаунтом и убедиться, что доска та же, затем через CLI сдвинуть задачу ещё раз и обновить SPA. Такая история наглядно доказывает главный тезис работы: универсальный REST API действительно обслуживает разные клиенты.

Я не подгонял отдельные «синтетические» цифры производительности и не выдавал разовые замеры за нагрузочное тестирование. Для курсового прототипа достаточны функциональная проверка, прохождение автотестов API и ручной сквозной сценарий. Если система стабильно поднимается и одинаково ведёт себя в трёх клиентах, практическая цель достигнута. Более глубокие perf-тесты имеют смысл уже после облачного деплоя и появления реальной нагрузки.

## 2.10. Результаты практической части

Получилось:

- рабочий backend Task Manager;
- Web SPA с основным пользовательским сценарием;
- Android-клиент;
- CLI-клиент;
- Docker Compose для воспроизводимого запуска;
- исправления дефектов, которые ломали демо (поиск задач в Postgres, закрытие dialog в SPA).

Ограничения: не все advanced-поля API выведены в каждый UI; Android покрывает базовый набор; облачный деплой — следующий этап.

Практическая часть подтвердила идею: для системы управления задачами важнее крепкий backend-контракт; ценность появляется, когда несколько клиентов работают с одними данными. Именно это я считаю главным инженерным результатом курсовой, а не количество экранов само по себе.

### Описание итогового результата

В итоговой версии системы пользователь проходит полный цикл работы с задачами без ручного вмешательства в базу данных. После регистрации и входа доступны организации, команды и проекты; у проекта создаётся доска с колонками; в колонках создаются и редактируются задачи; задачи перемещаются между колонками; приглашения и роли ограничивают доступ. ### Как проверить поставку

1. Поднять стенд командой Compose и дождаться healthy у API.  
2. Открыть Web SPA, зарегистрировать пользователя, создать проект с доской и задачей.  
3. Войти в Android под тем же пользователем и убедиться, что проект и доска видны.  
4. Через CLI переместить задачу в другую колонку.  
5. Обновить доску в Web SPA и увидеть задачу в новой колонке.

Итог: один REST API и три рабочих клиента, воспроизводимый запуск через Docker, согласованные данные между интерфейсами.

Отдельно зафиксирую, что именно я считаю доказательством готовности прототипа. Во-первых, API отвечает на health и принимает регистрацию/вход. Во-вторых, предметный сценарий не требует ручных SQL-вставок: проект, доска, колонки и задачи создаются через клиенты. В-третьих, один и тот же пользовательский контекст (JWT) работает в Web, Android и CLI. В-четвёртых, перемещение задачи через CLI отражается в Web SPA без отдельной «синхронизации вручную». Эти четыре проверки покрывают и сервер, и контракт, и согласованность клиентов.

Ограничения поставки тоже лучше назвать прямо: Android не повторяет весь UX Web один в один; часть advanced-полей API сильнее раскрыта на сервере, чем в мобильном интерфейсе; облачный деплой не входит в обязательный контур курсовой. При этом границы не ломают основной тезис работы — универсальный REST API уже обслуживает несколько клиентов и роли пользователей.

# БИЗНЕС-КЕЙС

## Проблема

Команды из 3–30 человек часто ведут работу в чатах и таблицах. Из-за этого:

- непонятен владелец задачи;
- сроки срываются незаметно;
- новичку трудно увидеть картину проекта;
- автоматизировать рутину почти нельзя;
- с телефона статус смотреть неудобно, если всё завязано на одну таблицу.

Платные зарубежные трекеры закрывают проблему, но для части команд в РФ они дорогие или неудобны по доступу. Отечественные SaaS есть, но кому-то важнее свой контур и простой API. В учебных и небольших продуктовых командах часто нет бюджета на тяжёлую систему, но уже есть боль от хаоса в переписке.

Отдельная сторона проблемы — инженерия. Даже если команда готова пользоваться готовым SaaS, ей нередко нужны интеграции: создать задачу из скрипта, выгрузить статус, проверить health сервиса. Если у инструмента слабый или закрытый API, автоматизация упирается в ручной труд. Поэтому в бизнес-кейсе Task Manager API — не «техническая деталь», а часть ценности.

## Целевая аудитория

1. Небольшие продуктовые и учебные команды (5–15 человек).  
2. Малый бизнес / агентства с проектами и дедлайнами.  
3. Технические команды, которым важны API и CLI.  
4. Компании, которым нужен self-hosted вариант.

Не целевая аудитория на старте — крупный enterprise с сотнями сложных workflow. Таким клиентам нужны глубокая аналитика, сложные согласования и зрелая поддержка; учебный прототип туда не целится.

## Ценностное предложение

Единое место для задач, досок и ролей; работа с компьютера и телефона; автоматизация через CLI/API; возможность поднять стенд через Docker. Коротко: лёгкий командный трекер с нормальным API и несколькими клиентами.

Для пользователя-непрограммиста ценность звучит как «видно, кто что делает». Для технического пользователя — как «можно интегрировать и автоматизировать». Совмещение этих двух обещаний как раз и отличает продукт от «просто доски» или «просто swagger-обёртки над таблицами».

В ценностном предложении важно не обещать «enterprise за неделю». Честнее формулировать так: Task Manager помогает небольшой команде быстро получить общий канбан, роли и API-доступ, а при необходимости развернуть это у себя через Docker. Такая формулировка ближе к реальному MVP и не создаёт ложных ожиданий относительно глубины Jira.

## Конкурентная позиция

| Сегмент | Примеры | Позиция |
|---------|---------|---------|
| Простой канбан | Trello | ближе по простоте доски |
| Тяжёлый IT-трекер | Jira, YouTrack | слабее по процессам, проще внедрить |
| РФ SaaS | Яндекс Трекер, Kaiten | self-hosted + открытый код |
| Таблицы/чаты | Sheets, Telegram | выигрыш за счёт статусов, ролей и API |

Ниша старта — между чатом/таблицей и тяжёлой системой, а не «убить Jira». Смысл позиции: забрать команды, которым уже тесно в мессенджере, но рано платить сложностью корпоративного трекера.

## MVP и монетизация

В курсовом MVP уже есть регистрация/вход, организации и команды, проекты, доски/задачи, роли, Web + Android + CLI, Docker. Для «боевого» MVP+ логичны облачный деплой, паритет Android с Web, биллинг (если SaaS), бэкапы и интеграции.

Варианты монетизации: self-hosted лицензия; SaaS-подписка; B2B-внедрение; отдельный тариф за API/automation. Реальный запуск потребовал бы юрлицо, оплату и поддержку — это за рамками курсовой.

Грубая экономика: расходы на маленький стенд — от сотен до тысяч ₽/мес. плюс время поддержки; гипотеза дохода 20 команд × 5 пользователей × 300–600 ₽/пользователь/мес. даёт порядок десятков тысяч ₽ выручки. Это проверка здравого смысла, а не финплан. Важно, что даже при осторожных оценках модель не выглядит заведомо абсурдной: рынок трекеров существует, а потребность в простом командном контуре повторяется из года в год.

## Риски и метрики

Риски: сильная конкуренция; ожидания «как в Jira»; нагрузка поддержки self-hosted; безопасность auth/ACL; выгорание соло-разработки. Ещё один риск — недооценка onboarding: если новый пользователь не создаст первую доску за несколько минут, продукт не «включится».

Метрики продукта: активация (первая доска и 5+ задач), retention 7/30 дней, доля команд со вторым пользователем. Для курсовой достаточно: система поднимается одной командой; сквозной сценарий проходит на Web, Android и CLI; права работают; репозиторий воспроизводим.

Вывод: проблема реальная, аудитория понятная, модель дохода представима. Курсовая закрывает технический MVP и архитектуру. С бизнес-точки зрения это проверка гипотезы «лёгкий multi-client трекер с сильным API нужен», а не готовый коммерческий запуск.

Если смотреть на кейс как на учебный бизнес-разбор, главный вывод простой. Рынок уже занят сильными игроками, поэтому стратегия «повторить Jira один в один» бессмысленна. Стратегия «закрыть боль маленькой команды простым self-hosted контуром с нормальным API» выглядит реалистичнее. Курсовой прототип как раз показывает техническую возможность такой стратегии: есть роли, доски, клиенты и воспроизводимый запуск. Коммерческая упаковка — отдельный следующий этап, который выходит за рамки дисциплины, но опирается на уже сделанный фундамент.

# ЗАКЛЮЧЕНИЕ

В курсовой работе я разобрал тему систем управления задачами, сравнил аналоги, обосновал стек, описал бизнес-кейс и реализовал рабочий прототип Task Manager. Центральной идеей остался универсальный REST API для многопользовательского управления задачами: один серверный контракт обслуживает Web SPA, Android и CLI.

На практике собрана схема «один REST API — три клиента». Backend на Spring Boot хранит данные в PostgreSQL, клиенты Web/Android/CLI работают через один контракт, окружение поднимается Docker Compose. Показан полный цикл: регистрация, оргструктура, проект, канбан, совместная работа и проверка через терминал. Исправлены дефекты, которые мешали стабильной демонстрации: проблема поиска задач на PostgreSQL и UX закрытия диалогов в SPA.

Цель работы достигнута. Я получил не только набор исходников, но и воспроизводимый стенд с понятным сценарием проверки. Дальше можно дотянуть Android ближе к Web, добавить CI/CD и облачный деплой, усилить отчётность и улучшить UX. Эти направления логично продолжают уже сделанную архитектуру и не требуют менять её фундамент.

Стек проекта совпадает с тем, что спрашивают в вакансиях Java/Spring и Android/Kotlin. Получился не набор разрозненных лабораторных, а один связный сервис. Для меня главный итог — опыт проектирования и реализации системы, где важны права доступа, согласованность клиентов и аккуратность серверного контракта.

В целом работа показала, что тема управления задачами хорошо подходит для курсового проекта полного цикла. Предметная область понятна без долгой подготовки, а техническая глубина достаточна: есть auth, сложная модель данных, несколько клиентов и контейнерный стенд. Универсальный REST API оказался не лозунгом, а рабочим принципом: одни и те же операции воспроизводятся из браузера, с Android и из командной строки. Именно это я считаю подтверждением того, что цель и задачи курсовой выполнены.

Если оценивать результат по критериям инженерной аккуратности, то важны не только «экраны», но и то, как устроен серверный контур: валидация входа, роли и режимы доступа, миграции схемы, единый формат ошибок, воспроизводимый Docker-стенд. Клиенты в такой схеме становятся сменяемыми: Web можно развивать отдельно от Android, а CLI остаётся быстрым способом проверить контракт. Для учебной работы этого достаточно, чтобы показать зрелый подход к проектированию, а не разовую сборку интерфейса вокруг одной страницы.

# ПРИЛОЖЕНИЕ

## Приложение А. Инструкция запуска

1. Установить Docker Desktop.  
2. В корне репозитория выполнить:  
   `docker compose -p taskmanager up --build -d`  
3. Web SPA: http://localhost:3000  
4. API health: http://localhost:8080/api/v1/health  
5. Android: эмулятор + APK, base URL `http://10.0.2.2:8080/api/v1`  
6. CLI:  
   `cd clients/cli`  
   `python tm.py health`

### Краткий runbook

Если health не отвечает, сначала проверить, запущен ли Docker Desktop и не заняты ли порты 8080 и 3000. Затем посмотреть статус контейнеров Compose и логи сервиса `api`. Если API стартовал, а SPA не открывается, проверить сервис `web-spa` и доступность порта 3000. Если Android не видит backend, проверить base URL (`10.0.2.2` для эмулятора или LAN-IP для устройства) и что API слушает `8080`. Если регистрация отклоняется, проверить формат email и требования к паролю.

После исправления окружения повторить проверку в порядке: health → login/register в CLI или SPA → создание проекта → создание задачи → move → обновление доски в Web.

## Приложение Б. Краткий глоссарий

- **API** — программный интерфейс сервера.  
- **JWT** — токен доступа после входа.  
- **Kanban** — доска с колонками и карточками.  
- **SPA** — одностраничное веб-приложение.  
- **CLI** — клиент командной строки.  
- **Docker Compose** — запуск набора контейнеров по одному файлу конфигурации.  
- **WIP** — ограничение числа задач «в работе».  
- **TEAM_ACL** — доступ к доске через состав команды.  
- **DTO** — объект передачи данных между API и клиентом.  
- **Liquibase** — инструмент миграций схемы БД.  
- **OpenAPI / Swagger** — описание и интерактивная документация REST API.  
- **Soft delete** — логическое удаление записи без физического стирания строки.  
- **OWNER / EDITOR / VIEWER / CONTRACTOR** — роли участника проекта с разным уровнем прав.

## Приложение А (дополнение). Обзор REST API

Базовый префикс: `/api/v1`. Аутентификация: `Authorization: Bearer <token>` после `login`/`register`.

Типовые группы endpoint’ов:

| Группа | Примеры операций |
|--------|------------------|
| Auth | регистрация, вход, выдача JWT |
| Organizations / Teams | создание организаций и команд, участники |
| Projects | создание проектов, роли, приглашения |
| Boards / Columns | доски, режимы доступа, колонки |
| Tasks | создание, редактирование, перемещение, поиск |
| Extra | метки, спринты, комментарии, чеклисты, уведомления |

Минимальный сквозной путь через API: `health` → `register`/`login` → создать проект с default board → создать задачу в колонке → `move` задачи в другую колонку. Этот путь одинаково воспроизводится из Web, Android и CLI и является практическим доказательством универсальности контракта.

### Приложение: расширенный runbook по типовым сбоям

1. **Compose не стартует.** Проверить, установлен и запущен ли Docker Desktop; убедиться, что виртуализация доступна; повторить `docker compose -p taskmanager up --build -d` после перезапуска Docker.  
2. **Порт занят.** Освободить `8080` или `3000`, либо остановить старые контейнеры того же проекта.  
3. **API unhealthy.** Смотреть логи контейнера `api`; типичные причины — база ещё не готова или ошибка миграций Liquibase.  
4. **Регистрация не проходит.** Проверить формат email и пароль; валидация на сервере отклоняет некорректный ввод осознанно.  
5. **Android не видит сервер.** Для эмулятора использовать `http://10.0.2.2:8080/api/v1`; для телефона — IP хоста в LAN и доступность порта.  
6. **Задача не находится после move.** Обновить доску в клиенте; данные меняются на сервере, локальный кэш UI сам по себе не является источником истины.

Этот runbook не заменяет чтение логов, но задаёт порядок действий: сначала окружение, потом auth, потом предметный сценарий. Такой порядок хорошо совпадает с архитектурой системы и ускоряет проверку поставки.
