# ВВЕДЕНИЕ

Современные команды разработки и проектные группы работают в условиях распределённой занятости, параллельных задач и необходимости прозрачного контроля сроков. Для организации такой работы широко применяются системы управления задачами (task / project trackers): от простых персональных списков до корпоративных платформ с ролями, досками Kanban, спринтами и интеграциями.

Цель курсовой работы — спроектировать и реализовать учебно-прикладную систему **Task Manager**: серверное REST API и набор клиентов (веб-приложение, мобильное приложение Android и консольный клиент), использующих один и тот же backend.

Для достижения цели решались следующие задачи:

1. проанализировать предметную область и аналогичные продукты;
2. обосновать выбор технологического стека;
3. спроектировать архитектуру «один API — несколько клиентов»;
4. реализовать серверную часть на Java / Spring Boot с аутентификацией, организациями, проектами, досками и задачами;
5. реализовать клиенты Web SPA, Android и CLI;
6. обеспечить локальное развёртывание через Docker Compose;
7. проверить работоспособность сквозными сценариями использования.

**Объект исследования** — программное обеспечение для командного управления задачами.  
**Предмет исследования** — методы проектирования и реализации многоклиентской системы на базе REST API.

Практическая значимость работы состоит в создании законченного прототипа, демонстрирующего полный цикл: от регистрации пользователя до совместной работы над задачами на разных платформах.

# ГЛАВА 1. ТЕОРЕТИЧЕСКАЯ ЧАСТЬ

## 1.1. Введение в предметную область

Системы управления задачами используются там, где результат работы зависит от нескольких людей и требуется видеть состояние процесса без постоянного уточнения в переписке. Их применяют не только программисты: в них ведут маркетинговые кампании, учебные групповые проекты, подготовку мероприятий, поддержку клиентов и внутренние процессы компании. Но для команды разработки такой инструмент особенно важен, поскольку одна задача может включать анализ требований, реализацию, проверку и выпуск.

В трекере задача является не просто заметкой. Она описывает ожидаемый результат, контекст, исполнителя, срок, приоритет и текущее состояние. Карточка «исправить ошибку авторизации» без условий воспроизведения почти бесполезна; карточка с описанием ошибки, ожидаемым поведением, приоритетом и ответственным уже позволяет начать работу. Поэтому качество системы определяется не количеством цветных колонок, а тем, насколько она помогает зафиксировать договорённость и не потерять её при смене участника.

У задачи обычно есть жизненный цикл. Автор создаёт её в начальной колонке, команда уточняет содержание, затем назначается исполнитель. После начала работы карточка перемещается в рабочую колонку, а после проверки — в завершённую. В зависимости от процесса может потребоваться возврат на доработку. Канбан делает этот поток наглядным: руководитель видит перегруженную колонку, исполнитель — свой список, а заказчик — уже достигнутые результаты. Scrum добавляет работу по итерациям: часть задач формирует спринт, а в конце оценивается выполненный объём.

Совместная работа невозможна без прав доступа. Владелец проекта создаёт его и управляет участниками. Редактор получает возможность менять рабочие объекты, наблюдатель — просматривать их, а внешний исполнитель может иметь ограниченный доступ. Доска также может быть открытой, закрытой или доступной определённой команде. Принципиально, что эти ограничения должны проверяться на сервере. Скрыть кнопку в браузере недостаточно: пользователь может вручную сформировать HTTP-запрос, поэтому окончательное решение о доступе принимает API.

Наличие нескольких клиентов меняет представление о системе. Веб-интерфейс удобен для планирования: на большом экране видны колонки, фильтры и много карточек. Android-клиент полезен для просмотра назначенной работы и быстрых действий вне рабочего места. CLI нужен прежде всего разработчику или администратору: через него удобно проверить доступность endpoint, подготовить данные или повторить сценарий без интерфейса. Все три клиента работают с одними и теми же ресурсами и не должны иметь собственных копий данных.

Поэтому в работе выбран API-first подход. Сначала определяется контракт: какие URL существуют, какие поля принимает запрос, какие коды ошибок возвращаются и какие операции разрешены авторизованному пользователю. Затем Web SPA, Android и CLI используют этот контракт. Такой подход уменьшает дублирование бизнес-логики: правило о том, что пользователь не может менять чужую закрытую доску, реализуется один раз на backend. Новый клиент можно добавить без изменения схемы БД и без переноса логики из другого интерфейса.

Системы управления задачами относятся к классу collaborative / project management software. Их базовая модель обычно включает:

- **пользователей** и **роли** (владелец, редактор, наблюдатель и т.п.);
- **проекты** как контейнеры работ;
- **доски** и **колонки** (часто в стиле Kanban: To do / Doing / Done);
- **задачи** с приоритетом, сроком, исполнителем, статусом;
- дополнительные сущности: метки, спринты, комментарии, уведомления, организации и команды.

Отдельное направление — подход **API-first**: сервер предоставляет стабильный контракт (REST), а интерфейсы (web, mobile, CLI, интеграции) развиваются независимо. Это особенно важно, когда один продукт должен работать и в браузере, и на смартфоне, и в автоматизации (скрипты DevOps).

В отличие от узкоспециализированных областей (например, геймдев или чистая мобильная разработка «ради UI»), задача курсовой лежит на стыке backend-инженерии, веб-клиентов и мобильной разработки: ценность создаётся не только экранами, но и корректной моделью доступа, согласованностью данных и возможностью подключать разные клиенты.

## 1.2. Актуальность проекта

Актуальность разработки собственной системы управления задачами определяется рядом факторов:

1. **Распределённая работа.** Команды всё чаще работают удалённо или гибридно; нужен общий источник правды по статусу задач.
2. **Мультиплатформенность.** Пользователь ожидает доступ с компьютера и телефона; инженеры — возможность автоматизировать операции через CLI.
3. **Контроль доступа.** В реальных продуктах важны организации, команды, приглашения и режимы доступа к доскам (открытая / закрытая / по составу команды).
4. **Учебно-практическая ценность.** Реализация такого сервиса покрывает широкий набор компетенций: проектирование API, безопасность, работа с БД, UI, контейнеризация.
5. **Импортозамещение и локальные решения.** На рынке РФ сохраняется интерес к отечественным и самостоятельно разворачиваемым трекерам задач, которые можно контролировать инфраструктурно.

Таким образом, проект Task Manager соответствует актуальным потребностям рынка и образовательным целям подготовки специалиста.

## 1.3. Актуальность выбранного технологического стека

Выбор технологий в работе связан с задачами системы, а не только с их популярностью. Сервер должен принимать параллельные HTTP-запросы, хранить связанные данные, проверять доступ и быть удобным для развёртывания. Клиенты должны работать с одинаковым JSON-контрактом на разных платформах. Поэтому стек разделён по ролям: Java и Spring Boot отвечают за серверную часть, PostgreSQL — за постоянное хранение, а браузерный, мобильный и консольный клиенты показывают разные способы использования одного API.

Java 17 — LTS-версия платформы с предсказуемой поддержкой и развитой экосистемой библиотек. Spring Boot 3.2 позволяет собрать REST-сервис из проверенных компонентов: web-слой, Spring Security, JPA, валидация и встроенный сервер. Однако фреймворк не является готовым трекером задач. Он ускоряет типовые технические операции, а правила предметной области всё равно проектируются отдельно: кто может войти в проект, что можно менять на доске и какие поля обязательны при создании задачи.

Реляционная PostgreSQL подходит для Task Manager лучше, чем хранение объектов в файлах. У проекта есть доски, у доски — колонки, у колонки — задачи; пользователь связан с организациями и проектами через участия. Внешние ключи и ограничения помогают не оставить задачу без существующей колонки или участника без существующего проекта. Транзакции важны при составных операциях: если создание проекта предполагает создание стандартной доски, результат должен сохраниться целиком либо откатиться.

Liquibase решает проблему эволюции схемы. В ходе разработки появляются таблицы, поля и индексы, и ручное изменение базы на одном компьютере не является воспроизводимым решением. Миграция хранится в репозитории рядом с кодом и применяется последовательно. Это особенно полезно при запуске через Docker: новая база получает ожидаемую структуру без дополнительных действий автора. H2 может использоваться для быстрых тестов, но проверка на PostgreSQL обязательна, потому что диалекты и работа функций не полностью совпадают.

JWT выбран как нейтральный механизм для SPA, Android и CLI. После логина клиент получает подписанный access token и отправляет его в `Authorization: Bearer ...`. Backend проверяет подпись и срок действия, определяет текущего пользователя и только после этого проверяет права на конкретный объект. Токен не следует воспринимать как замену авторизации: действующий пользователь не может автоматически редактировать любой проект. В реальном продукте можно развивать схему refresh-токенами и отзывом сессий, но для учебной системы важна корректная базовая проверка.

Веб-клиент написан на vanilla JavaScript намеренно. Фреймворк React или Vue был бы оправдан в большом интерфейсе, но добавил бы систему сборки и дополнительный слой абстракции. Здесь легче показать путь запроса: действие пользователя вызывает `fetch`, токен попадает в заголовок, ответ преобразуется в состояние интерфейса. Nginx раздаёт статические файлы на порту 3000. Kotlin, OkHttp и coroutines на Android демонстрируют ту же операцию в нативном клиенте, а Python CLI доказывает самодостаточность API без графического интерфейса.

В проекте использован следующий стек:

| Уровень | Технологии |
|--------|------------|
| Backend | Java 17, Spring Boot 3.2, Spring Security, Spring Data JPA, Validation |
| Безопасность | JWT (jjwt) |
| БД и миграции | PostgreSQL 16, Liquibase; H2 для тестов |
| Документация API | Springdoc OpenAPI (Swagger UI) |
| Web-клиент | HTML, CSS, JavaScript (SPA), Nginx |
| Android-клиент | Kotlin, Android SDK 34, OkHttp, Gson, Coroutines, Material Design |
| CLI | Python 3 (argparse, urllib) |
| Инфраструктура | Docker, Docker Compose |

Почему стек актуален:

- **Java / Spring Boot** — один из доминирующих стеков корпоративного backend в банках, ритейле, телекоме и продуктовых компаниях.
- **PostgreSQL** — зрелая реляционная СУБД, стандарт де-факто для транзакционных приложений.
- **JWT + REST** — распространённая схема для SPA и мобильных клиентов без серверных сессий на каждом запросе.
- **Kotlin / Android** — основной язык современной нативной Android-разработки.
- **Python CLI** — привычный инструмент для скриптов, администрирования и демонстрации API «без UI».
- **Docker Compose** — воспроизводимый запуск всего окружения одной командой, навык, востребованный в DevOps и backend-разработке.

Стек выбран не «модный ради моды», а как типичный производственный набор для систем класса task tracker.

## 1.4. Популярные аналоги разрабатываемого продукта

Ниже приведены наиболее известные аналоги. Для курсовой важны не полные копии коммерческих продуктов, а сопоставление ключевых возможностей.

### Jira (Atlassian)
- **Назначение:** корпоративный трекер задач и процессов разработки.  
- **Сильные стороны:** гибкие workflow, роли, интеграции, отчёты.  
- **Стек (публично известный профиль):** крупные enterprise-системы, облачная и server/Data Center линейки; сложный продуктовый стек Atlassian.  
- **Отличие от курсовой:** промышленный масштаб; у Task Manager — учебный прототип с упором на API и несколько клиентов.

### Trello (Atlassian)
- **Назначение:** визуальные Kanban-доски.  
- **Сильные стороны:** простота, карточки, колонки, удобный UX.  
- **Отличие:** меньше «тяжёлой» оргструктуры; в Task Manager есть организации, команды, ACL досок, роли проекта.

### Asana
- **Назначение:** управление работой команд, списки и доски, сроки.  
- **Сильные стороны:** удобство для продуктовых и маркетинговых команд.  
- **Отличие:** закрытый SaaS; курсовой проект — открытый учебный код и локальный/контейнерный запуск.

### YouTrack (JetBrains)
- **Назначение:** трекер задач, удобный для команд разработки.  
- **Сильные стороны:** гибкая модель полей, поиск, интеграция с экосистемой JetBrains.  
- **Отличие:** готовый коммерческий продукт; Task Manager демонстрирует самостоятельную реализацию ядра.

### Яндекс Трекер / Kaiten и др.
- **Назначение:** решения для командной работы, востребованные на рынке РФ.  
- **Сильные стороны:** локализация, соответствие практикам отечественных компаний.  
- **Отличие:** продукт «из коробки»; курсовая показывает полный цикл разработки своего сервиса.

**Вывод по аналогам.** Коммерческие системы богаче по отчётам, интеграциям и масштабу. Курсовой Task Manager реализует ядро предметной области (auth, org/team, project, board/column/task, invites, labels/sprints, multi-client) и пригоден как демонстрационный прототип и база для дальнейшего развития.

Сравнение с Jira показывает, почему в учебном проекте нельзя измерять качество только числом функций. Jira рассчитана на множество проектов, сложные схемы переходов, интеграции с репозиториями, сервис-деском и корпоративной отчётностью. По публичным материалам Atlassian облачная инфраструктура использует AWS и внутреннюю PaaS Micros; в командах встречаются Java/Kotlin, Node.js и Python, а для фронтенда — React. Повторить такую платформу в рамках курсовой было бы нецелесообразно. Важно воспроизвести архитектурный принцип: данные и правила находятся за API, а клиент является заменяемым представлением.

Trello полезен как пример понятного канбана. Его сила — низкий порог входа: пользователю достаточно создать доску, колонки и карточки. В Task Manager сохранена эта базовая модель, но добавлены проектный контекст, роли и режимы доступа. Это делает систему сложнее Trello, но приближает к ситуации, когда карточки принадлежат не одному человеку, а организации с несколькими командами. При этом интерфейс не должен заставлять пользователя изучать администрирование до создания первой задачи.

Asana иллюстрирует, что приложение совместной работы может быть удобным не только для разработчиков. В публичном описании её стека упоминаются TypeScript/React, LunaDb на Scala, Node-based LunaServer и MySQL-backed persistence. Для данной работы важен не выбор конкретных языков Asana, а разделение ответственности: богатый интерфейс и серверное хранилище развиваются независимо при наличии стабильного контракта. Task Manager следует этому принципу в упрощённой форме: Web, Android и CLI не знают внутреннее устройство JPA-слоя.

YouTrack близок по целевой аудитории инженерных команд. JetBrains публично связывает продукт с JVM/Java и JavaScript; исторически в материалах упоминаются MPS и Jersey REST. Его преимущества — гибкие поля, поиск и работа с разработческим контекстом. В учебной системе реализован более узкий набор, но он уже включает поиск задач, метки, спринты и доступы. Яндекс Трекер и Kaiten, в свою очередь, подтверждают практический спрос на русскоязычные и самостоятельно контролируемые решения. Они не являются «конкурентами» курсовой работы, а задают ориентир предметной области.

## 1.7. Теоретические сведения о технологиях проекта

### Проектирование REST-контракта

Контракт API описывает не только URL. Он определяет структуру входных данных, ответа, правила ошибок и способ авторизации. Например, `GET` списка задач не должен изменять данные, а `POST` создания задачи должен вернуть созданный объект либо понятную ошибку валидации. Версия `/api/v1` в пути даёт возможность позже добавить несовместимую версию, не ломая уже установленный клиент. Документация OpenAPI полезна тем, что запросы можно проверить через Swagger без написания отдельной программы.

Коды HTTP являются частью диалога между сервером и клиентом. `200 OK` означает успешное чтение, `201 Created` — создание, `400 Bad Request` — неправильные данные, `401 Unauthorized` — отсутствие или неверный токен, `403 Forbidden` — недостаточно прав, `404 Not Found` — объект не найден. Возвращать 500 на обычную ошибку пользователя неправильно: интерфейс не понимает, что исправить, а разработчик теряет точку диагностики. В проекте обработка повреждённого JSON была приведена к корректному ответу 400.

### Слои Spring-приложения

Контроллер принимает запрос и преобразует его в DTO. Сервис реализует правило предметной области: находит объекты, проверяет роль, изменяет состояние. Репозиторий выполняет доступ к данным через JPA. Такое разделение облегчает тестирование и предотвращает ситуацию, когда вся логика скрыта в одном endpoint. DTO отделяют публичный JSON от JPA-сущностей: наружу не попадают технические поля, а запрос содержит только разрешённые для изменения значения.

Валидация имеет два уровня. На техническом уровне проверяются обязательность названия, формат email, длина пароля и типы полей. На бизнес-уровне проверяется смысл операции: пользователь не должен назначать исполнителем человека из другой организации или изменять закрытую доску без прав. Второй уровень нельзя заменить аннотациями DTO, потому что он требует обращения к текущим данным и пользователю из `SecurityContext`.

### Данные, запросы и миграции

JPA отображает классы на таблицы и позволяет работать со связями объектов, но не отменяет знания SQL. Нужны аккуратные отношения, понятные каскады и контроль загрузки коллекций. Запрос поиска должен учитывать пустую строку и отсутствие фильтра. Практическая ошибка `function lower(bytea) does not exist` возникла при отличии поведения на PostgreSQL: значение `null` в выражении с `LOWER` и `LIKE` оказалось неподходящим. Передача пустой строки и явная проверка `:q = ''` сделали `GET /api/v1/columns/{id}/tasks` стабильным. Это показывает, почему тесты на H2 нельзя считать полной заменой контейнерного PostgreSQL.

Liquibase хранит историю изменения схемы в виде changeset. Каждый changeset описывает небольшое действие: создать таблицу, добавить колонку, индекс или ограничение. При следующем запуске уже применённые изменения повторно не выполняются. Благодаря этому база в Docker соответствует версии приложения, а демонстрационный стенд не зависит от ручной настройки.

### Безопасность и работа клиентов

JWT содержит сведения, необходимые для идентификации, и подпись, защищающую их от незаметной подмены. Пароль в токен не включается. Security-фильтр выделяет Bearer-токен из заголовка, проверяет его, после чего запрос проходит к контроллеру уже с известным пользователем. Даже в этом случае сервис обязан проверить членство в проекте. Защита не должна строиться на скрытом CSS-элементе или на том, что мобильный клиент «не показывает» опасную функцию.

SPA хранит отображаемое состояние и обновляет его после ответов API. При `401` интерфейс переводит пользователя к повторному входу, при `403` сообщает о запрете, при сетевой ошибке не выдаёт её за бизнес-ошибку. На Android сетевой вызов выполняется не в главном потоке: coroutines позволяют дождаться OkHttp-ответа в фоновом контексте и затем безопасно обновить экран. В эмуляторе `10.0.2.2` — специальный адрес хост-компьютера; обычный `localhost` указывал бы на сам эмулятор.

### REST и клиент-серверная архитектура
REST (Representational State Transfer) — стиль взаимодействия, при котором ресурсы адресуются URI, а операции выражаются методами HTTP (GET, POST, PUT/PATCH, DELETE). Для Task Manager выбран префикс `/api/v1`, что упрощает эволюцию контракта.

### Spring Boot
Spring Boot упрощает создание production-ready приложений: автоконфигурация, встроенный сервер (Tomcat), интеграция Security, Data JPA, Validation. Версия 3.x опирается на Jakarta EE API и Java 17+.

### Spring Security и JWT
JWT (JSON Web Token) — компактный токен с подписью. После login/register клиент передаёт `Authorization: Bearer <token>`. Сервер проверяет подпись и извлекает субъекта (пользователя), не храня серверную сессию на каждый запрос (stateless-подход удобен для SPA и mobile).

### JPA и PostgreSQL
JPA/Hibernate отображает объекты Java на таблицы БД. PostgreSQL обеспечивает надёжное хранение связей (проекты → доски → колонки → задачи) и ограничений целостности. Миграции схемы выполняются Liquibase.

### Web SPA
Single Page Application загружает оболочку страницы и далее обновляет UI через JavaScript и вызовы API. В проекте SPA реализована без тяжёлого фреймворка (vanilla JS), что снижает порог развёртывания (статические файлы + Nginx).

### Android-клиент
Android-приложение строится на Activities и ViewBinding, сетевой слой — OkHttp, сериализация — Gson, асинхронность — Kotlin Coroutines. Для доступа к API на эмуляторе используется адрес хоста `10.0.2.2`.

### CLI
Консольный клиент на Python вызывает те же endpoint’ы, что и GUI-клиенты. Это демонстрирует независимость API от конкретного UI и полезно для smoke-тестов и автоматизации.

### Docker Compose
Контейнеризация упаковывает API, PostgreSQL, Web SPA и CLI-окружение в единый стек. Это снижает проблему «у меня работает локально» и упрощает демонстрацию преподавателю.

# ГЛАВА 2. ПРАКТИЧЕСКАЯ ЧАСТЬ

## 2.1. Постановка задачи и требования

Необходимо реализовать систему, в которой:

1. пользователь регистрируется и входит по JWT;
2. можно создавать организации, добавлять участников, формировать команды;
3. можно создавать проекты (личные или в рамках организации), доски и колонки;
4. можно создавать и вести задачи (приоритет, срок, исполнитель, тип, статус), перемещать их по колонкам;
5. поддерживаются приглашения в проект, уведомления, метки и спринты (в объёме реализованного API/клиентов);
6. доступны клиенты: **Web SPA**, **Android**, **CLI**;
7. система поднимается через **Docker Compose** (API + Postgres + SPA + CLI-контейнер).

Нефункциональные требования: понятный REST-контракт, проверка прав доступа, возможность демонстрации сквозного сценария на нескольких клиентах.

## 2.2. Архитектура системы

Архитектура — **многоклиентская**, с единым backend:

```
[ Web SPA :3000 ] ----\
[ Android app     ] ---->  [ Spring Boot API :8080 ]  --->  [ PostgreSQL :5432 ]
[ CLI (Python)    ] ----/
```

Ключевые принципы:

- единый контракт `/api/v1`;
- аутентификация через JWT;
- разграничение доступа на уровне проектов, досок и ролей;
- клиенты не содержат бизнес-логики предметной области «в обход» API.

Дополнительно в составе API присутствует демонстрационный серверный UI на Thymeleaf (тот же порт `:8080`), однако основным веб-клиентом для демонстрации выбран SPA.

## 2.3. Модель данных и основные сущности

Основные сущности предметной области:

- **User** — пользователь системы;
- **Organization** — организация (тип LOCAL / COMMERCIAL и др. по модели API);
- **Team** — команда внутри организации;
- **Project** — проект; роли участников (OWNER / EDITOR / VIEWER / CONTRACTOR и др.);
- **Board** — доска; режимы доступа OPEN / PRIVATE / TEAM_ACL;
- **BoardColumn** — колонка доски;
- **Task** — задача (title, description, priority, status, deadline, assignee, type и др.);
- **Label**, **Sprint** — классификация и итерации;
- **Invitation**, **Notification**, комментарии и чеклисты — поддержка совместной работы.

Связи типичны для трекера: проект содержит доски, доска — колонки, колонка — задачи; пользователи связаны с организациями, командами и проектами через membership/roles.

## 2.4. Реализация серверной части (API)

Сервер реализован на **Spring Boot 3.2 / Java 17**.

Практическая реализация начинается с модуля аутентификации. Пользователь передаёт регистрационные данные или пару email/пароль; сервер валидирует вход, сохраняет пользователя и при успешном входе выдаёт JWT. Все последующие операции получают текущего пользователя из security context. Благодаря этому клиент не передаёт в каждом запросе «своего» пользователя как доверенное поле, а backend сам определяет, от чьего имени выполняется действие.

Типовой серверный поток для создания задачи выглядит так. Контроллер получает DTO с названием, описанием, приоритетом, сроком и идентификатором колонки. Сервис загружает колонку и связанный проект, проверяет право текущего пользователя на редактирование, валидирует исполнителя и только затем создаёт запись. В ответ возвращается DTO задачи. Аналогично перемещение между колонками не является простым изменением чужого id: сервер убеждается, что обе колонки доступны в пределах разрешённого проекта. Это особенно важно при наличии PRIVATE и TEAM_ACL досок.

Обработка исключений вынесена в единый слой, поэтому клиент получает предсказуемые ошибки. Неверные поля, отсутствующая сущность и отказ доступа не маскируются под одну универсальную «ошибку сервера». Такая схема значительно упрощает клиентскую часть: Web SPA и Android могут показать понятное сообщение, а CLI — вывести код и текст в терминал. Отдельно проверялись случаи пустого тела, повреждённого JSON и запроса без токена.

Миграции Liquibase запускаются вместе с приложением. При чистом PostgreSQL сначала создаётся структура, затем API получает возможность работать с данными. При повторном старте изменения не дублируются. В профиле `prod` параметры подключения передаются контейнерному приложению, поэтому сервер не зависит от локальной установленной базы. Обнаруженная ошибка с `lower(bytea)` была найдена именно в таком окружении: запрос без `q` открывал колонку с задачами и мог завершиться 500. После нормализации пустого поиска в `""` сценарий стал стабильно возвращать 200.

Состав функциональности backend (ключевое):

- регистрация и вход, выдача JWT;
- CRUD и операции по организациям, командам, проектам, доскам, колонкам, задачам;
- приглашения и принятие/отклонение;
- поиск задач, лента активности, уведомления;
- фильтры задач, работа с метками и спринтами;
- обработка ошибок с корректными HTTP-кодами (в т.ч. 400 на некорректное тело запроса);
- миграции Liquibase;
- профиль `prod` для PostgreSQL в Docker.

Пример исправления, существенного для стабильности: при выборке задач PostgreSQL некорректно обрабатывал `null` в параметре текстового поиска (`lower(bytea)`). В сервисе запросов пустой поиск передаётся как пустая строка, что устраняет 500-ошибки при открытии колонок без фильтра `q`.

## 2.5. Клиент Web SPA

**Стек:** HTML + CSS + JavaScript, раздача Nginx, порт `:3000`.

Web SPA является основным клиентом для визуальной демонстрации. После входа пользователь получает список доступных организаций и проектов. Создание проекта может сопровождаться созданием доски по умолчанию, затем на доске появляются колонки и карточки. При создании или редактировании карточки интерфейс собирает данные формы, отправляет их в API с JWT и после успешного ответа обновляет видимый список. Таким образом, браузер не хранит отдельную «истинную» модель задач — источником данных остаётся сервер.

Для интерфейса важно различать ошибку сети и ответ API. Если API вернул 403, пользователю объясняется, что действие запрещено его ролью; если сеть недоступна, сообщение не должно выглядеть как ошибка заполнения формы. После перемещения задачи интерфейс повторно получает или обновляет данные соответствующих колонок, поэтому результат сразу согласован с Android и CLI. В ходе работы исправлено CSS-правило для `<dialog>`: закрытое окно не должно оставаться flex-элементом. Условие `dialog[open]` устранило видимые внизу страницы кнопки закрытого диалога.

Возможности, демонстрируемые в SPA:

- регистрация / вход;
- разделы проектов и организаций;
- создание проекта с доской по умолчанию;
- канбан: создание задач, редактирование атрибутов, перемещение между колонками;
- работа с организациями, командами, приглашениями;
- комментарии / чеклист / подсказки DoD (в объёме UI);
- уведомления и поиск (где реализовано в UI).

Исправлен UX закрытых модальных окон: правило CSS `dialog { display: flex }` перекрывало поведение закрытого `<dialog>`; отображение flex применяется только к `dialog[open]`.

## 2.6. Клиент Android

**Стек:** Kotlin, minSdk 26, compileSdk/targetSdk 34, OkHttp, Gson, Coroutines, Material.

Мобильный клиент проверяет, что контракт не зависит от браузера. В `AuthActivity` пользователь проходит регистрацию или вход, после чего приложение сохраняет данные, необходимые для авторизованных запросов. `HomeActivity` показывает доступные проекты и организации, экраны деталей позволяют перейти к нужному проекту и доске. В `BoardActivity` пользователь получает колонки и задачи с сервера, может создать новую колонку или карточку. Запросы выполняются через OkHttp, преобразование JSON выполняет Gson, а coroutines не блокируют главный поток интерфейса.

При запуске на эмуляторе API доступно по `10.0.2.2:8080`, а не по `localhost`: это адрес виртуального маршрута от эмулятора к хост-машине. Данный факт был проверен отдельным сценариям входа и загрузки проектов. Мобильный UI намеренно не заявляется как полная копия SPA. Наиболее сложные действия, включая удобное drag-and-drop, расширенный поиск и часть приглашений, лучше покрыты Web или CLI. При этом базовый путь «войти — открыть проект — посмотреть доску — создать задачу» работает с теми же данными и подтверждает кроссплатформенность решения.

Экраны (Activities):

- `AuthActivity` — регистрация и вход;
- `HomeActivity` — проекты и организации;
- `OrgDetailActivity` / `ProjectDetailActivity` — детали;
- `BoardActivity` — просмотр доски, создание колонок/задач.

На эмуляторе базовый URL API: `http://10.0.2.2:8080/api/v1`.

Ограничение текущей версии UI: акцент на создание и просмотр; часть функций (полноценный drag-and-drop, поиск, принятие приглашений) сильнее раскрыта в Web/CLI. Для курсовой это допустимо при честном описании границ реализации.

## 2.7. Клиент CLI

**Стек:** Python 3, стандартная библиотека (`argparse`, `urllib`), скрипт `tm.py`.

Консольный клиент организован как набор явных команд, а не как отдельная версия бизнес-логики. `argparse` разбирает параметры, `urllib` выполняет HTTP-запрос, а токен после входа подставляется в заголовок. Это полезно для диагностики: если команда создания задачи вернула ожидаемый JSON, но Web её не показывает, источник проблемы вероятнее находится в интерфейсе или его состоянии, а не в сервере. CLI также удобен для повторяемой демонстрации, поскольку команды можно выполнить в заранее известном порядке.

Сквозной пример выглядит так: создаётся пользователь-владелец, затем проект с доской и колонками, в первой колонке создаётся задача «Сделать отчёт», после чего она переносится в следующую колонку. Когда в браузере обновляется та же доска, карточка видна уже в новом месте. Такая проверка не зависит от ручного переноса данных между программами: изменённый объект один и хранится в PostgreSQL. Поиск командой `search` дополнительно показывает работу фильтра, которая проверялась после исправления PostgreSQL-ошибки.

Типовой демонстрационный сценарий:

```bash
python tm.py health
python tm.py register --email owner@demo.com --password secret12 --name Owner
python tm.py login --email owner@demo.com --password secret12
python tm.py whoami
python tm.py projects --create "CLI Demo" --with-default-board --template KANBAN
python tm.py boards <projectId>
python tm.py columns <boardId>
python tm.py tasks <columnId> --create "Сделать отчёт" --priority HIGH
python tm.py move <taskId> --column <otherColumnId>
python tm.py search <projectId> --q отчёт
```

CLI показывает, что API самодостаточно: те же операции выполняются без графического интерфейса, а результат виден в Web SPA.

## 2.8. Развёртывание и эксплуатация

Локальный стек поднимается командой вида:

Перед запуском Docker Compose собирает образы и создаёт общую сеть сервисов. Контейнер `api` ожидает доступность PostgreSQL и подключается к нему по имени сервиса, а `web-spa` публикует статический интерфейс. Снаружи контейнерной сети пользователю нужны только опубликованные порты: 3000 для браузера и 8080 для API. Такой состав достаточен для демонстрации и не требует установки Java, Node.js или PostgreSQL на компьютере проверяющего, если установлен Docker Desktop.

После старта целесообразно сначала вызвать endpoint здоровья, затем открыть SPA и только потом проверять сложные сценарии. Если health не возвращает `UP`, нет смысла искать проблему в Android или CSS: следует проверить логи и состояние API/БД. Если API отвечает, но Web не открывается, отдельно проверяется контейнер Nginx и порт 3000. Такое разделение упрощает диагностику и показывает понимание того, что клиент, сервер и хранилище являются разными компонентами.

```bash
docker compose -p taskmanager up --build -d
```

Сервисы:

| Сервис | Назначение | Порт |
|--------|------------|------|
| postgres | СУБД | 5432 |
| api | Spring Boot | 8080 |
| web-spa | Nginx + SPA | 3000 |
| cli | окружение CLI | — |

Проверка здоровья API: `GET /api/v1/health` → `{"status":"UP"}`.

Варианты бесплатного хостинга для публикации (вне обязательного объёма курсовой): Render (API + Postgres + static SPA), Oracle Cloud Always Free (VM + Docker Compose), отдельный бесплатный Postgres (например Neon) + PaaS для API. Для защиты достаточно стабильного локального/контейнерного запуска и видео-демонстрации.

## 2.9. Тестирование и демонстрация

Проверка выполнялась на нескольких уровнях:

Тестирование строилось не только вокруг отдельных endpoint, но и вокруг пользовательских цепочек. Минимальная цепочка включает регистрацию, получение токена, создание проекта, получение доски и колонок, создание задачи, выборку задач и изменение колонки. Для каждого шага проверяется HTTP-статус и полученный JSON. Такой smoke-тест особенно полезен после пересборки контейнеров: он быстро отвечает на вопрос, работает ли система как единое целое.

Отдельно проверялись отрицательные сценарии: запрос без JWT, обращение к несуществующему объекту, пустые или неверные значения формы, попытка открыть закрытый ресурс без необходимых прав. В пользовательском интерфейсе вручную тестировались вход, создание сущностей, открытие и закрытие модальных окон, отображение ошибок. На Android проверялась связь с запущенным API и отсутствие блокировки экрана во время сетевого запроса. Успешным считался не только ответ 200, но и корректное отображение результата на втором клиенте.

1. **Автотесты API** (Maven) — проверка ключевых сценариев и обработки ошибок.
2. **Smoke через CLI/HTTP** — регистрация, проект, доска, задача, список задач колонки.
3. **Ручная проверка Web SPA** — канбан, модальные окна, совместные сценарии.
4. **Android на эмуляторе** — вход, проекты, создание задач при работающем API.

Рекомендуемый сценарий защиты/видео:

1. поднять Docker-стек;
2. показать Web: оргструктура → проект → канбан;
3. показать Android: тот же API с телефона/эмулятора;
4. показать CLI: создание/перемещение задачи и отражение в Web;
5. кратко назвать стек каждого клиента.

## 2.10. Результаты практической части

В результате практической работы получено:

Практический результат оценивается по сквозному сценарию, а не только по наличию исходных файлов. После запуска compose пользователь может обратиться к endpoint здоровья, зарегистрироваться через один из клиентов, выполнить вход, создать проект и доску, добавить колонку и задачу. Изменение задачи через CLI сохраняется в PostgreSQL и затем видно в Web SPA; Android обращается к тому же API и получает доступные ему проекты. Тем самым проверяется центральное требование — одна система с несколькими клиентами, а не три независимых демонстрации.

Архитектура также показала разделение зон ответственности. Backend содержит проверку JWT, прав доступа, валидацию и операции с данными. Web SPA отвечает за удобный канбан и формы, Android — за мобильный путь просмотра и создания, CLI — за быстрые воспроизводимые команды. Если потребуется добавить ещё один клиент, например desktop-приложение, ему не нужно будет напрямую подключаться к PostgreSQL или повторять правила ролей: достаточно использовать документированный REST API.

Во время работы были получены не только положительные результаты, но и опыт диагностики. Ошибка поиска, проявившаяся на PostgreSQL как `lower(bytea)`, не была заметна лишь по внешнему виду интерфейса. Для её локализации требовалось воспроизвести запрос на контейнерном стенде и сравнить поведение при пустом параметре. Исправление нормализовало пустой поиск и исключило падение при открытии колонки. Второй пример — модальное окно SPA: закрытый `<dialog>` оставался видимым из-за слишком общего CSS-правила. Изменение селектора на `dialog[open]` устранило дефект без изменения серверной части. Такие случаи показывают, что тестирование многоклиентского приложения должно охватывать и API, и конкретный UI.

Границы проекта определены осознанно. В промышленном сервисе потребовались бы более полный аудит действий, централизованное логирование, метрики, резервное копирование БД, CI/CD, управление refresh-токенами, уведомления в реальном времени и расширенная проверка конкурентных изменений. Также можно развить фильтры, отчётность по срокам, WIP-лимиты и полный функциональный паритет Android с веб-клиентом. Эти направления не отменяют текущий результат: базовый контур управления задачами уже реализован, запускается воспроизводимо и допускает дальнейшее развитие без смены основных границ архитектуры.

- работающий backend Task Manager на Spring Boot с PostgreSQL;
- веб-клиент SPA с основным пользовательским сценарием;
- Android-клиент для мобильного доступа;
- CLI-клиент для терминальных операций и проверки API;
- воспроизводимое окружение Docker Compose;
- устранённые дефекты, критичные для демо (ошибка выборки задач в PostgreSQL; «залипание» кнопок закрытого dialog в SPA).

Ограничения: не все advanced-функции API выведены в каждый UI; Android покрывает базовый набор операций; облачный деплой не является обязательной частью текущей поставки.
